# Database

## 1. Stack

- PostgreSQL 17.
- Drizzle ORM with the `postgres` (postgres.js) driver.
- Migrations generated by `drizzle-kit` into `drizzle/`, reviewed, and committed.

## 2. Where tables live

Each module defines its tables in `src/modules/<module>/infrastructure/<module>.tables.ts`. `src/shared/database/schema.ts` re-exports every module's tables so Drizzle and `drizzle-kit` see one schema.

Only repositories (`*.repository.ts`) query tables. Services call repositories.

## 3. Conventions

| Topic | Rule |
|---|---|
| Table names | snake_case, plural: `meta_assets` |
| Primary keys | `id uuid` generated in the application as **UUID v7** (time-ordered, index-friendly) |
| Tenancy | Every business table has `workspace_id uuid not null` with a foreign key; composite indexes start with `workspace_id` |
| Timestamps | `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()` updated by the repository |
| Soft delete | `deleted_at timestamptz` only where history matters (campaigns, creatives); otherwise hard delete |
| Money | `bigint` minor units (paise) plus `currency char(3)` |
| Enums | Postgres enums for small, stable sets; text with a check constraint when values may grow often |
| JSON | `jsonb` only for external payload snapshots (Meta responses) or flexible settings, never for data we filter on often |
| Secrets | Never stored in plain text: refresh tokens and OTP codes are hashed, Meta tokens are AES-256-GCM encrypted |
| Foreign keys | Always declared; `on delete cascade` from workspace to its data |

## 4. Performance

- Indexes for every list and lookup path, written next to the table definition.
- Prepared statements (`.prepare()`) for the hottest queries such as session and asset lookups.
- No N+1 queries: joins or `inArray` batch loads.
- Large time-series tables (`ad_insights_daily`) are partitioned by month and read through summary tables.
- Transactions via `db.transaction()` in services when several writes must succeed together.

## 5. Migrations workflow

```bash
npm run db:generate -- --name add_refresh_tokens
npm run db:migrate
```

1. Change or add tables in `*.tables.ts`.
2. Generate a migration and read the SQL.
3. Apply locally, run tests, commit the migration with the code.
4. Production applies migrations in a release step before new instances start.

Destructive changes (dropping or renaming columns) are done in two releases: add the new column and dual-write, then remove the old one.

|---|---|---|
| `users` | iam | `phone` unique, `name`, `last_login_at` |
| `workspaces` | iam | `name`, `owner_id` |
| `workspace_members` | iam | `workspace_id`, `user_id`, `role`; unique (`workspace_id`, `user_id`) |
| `otp_challenges` | auth | `phone`, `code_hash`, `attempts`, `expires_at`, `consumed_at`, `ip`; index (`phone`, `created_at`) |
| `refresh_tokens` | auth | `user_id`, `family_id`, `token_hash` unique, `expires_at`, `replaced_at`, `revoked_at`, `user_agent`, `ip` |
| `meta_connections` | meta | `workspace_id` unique, `token_ciphertext`, `token_last4`, `system_user_id`, `system_user_name`, `granted_scopes`, `status`, `checked_at` |
| `meta_assets` | meta | `workspace_id`, `kind` (`business`, `ad_account`, `page`, `instagram`, `dataset`), `external_id`, `name`, `data` jsonb, `is_primary`; unique (`workspace_id`, `kind`, `external_id`) |
| `onboarding_progress` | onboarding | `workspace_id`, `step`, `status`, `completed_at`; unique (`workspace_id`, `step`) |
| `idempotency_keys` | shared | `workspace_id`, `key`, `request_hash`, `response`, `expires_at` |
| `audit_events` | shared | `workspace_id`, `actor` (`user`, `system`, `ai`), `action`, `target`, `data`, `created_at` |
